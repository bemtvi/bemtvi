# Macros (`<F2>` / `<F3>`)

Status: **plan** — 2026-08-14.

Vim's keyboard macros are the last big gap in the normal-mode grammar
(`docs/known-approximations.md` still lists them as missing). This plan lands
them in four reviewable phases.

## What we are building

```
<F2>{reg}     start recording typed keys into register {reg}  (uppercase appends)
<F2>          stop recording (Normal mode only)
<F3>{reg}     execute register {reg} as keys                  ({count}<F3>a repeats)
<F3><F3>      re-execute the last register played
<F3>:         re-execute the last ex command
```

**Not on `q` / `@`.** The behaviour is vim's; the bindings are bemtvi's. `q` is
the close key half the read-only surfaces already bind, and vim's `q` shadows it
for every user who never records a macro — so the trigger moves to a key nothing
else wants. The vim spelling is one line of config away:

```lua
btv.keymap.set("n", "q", "<F2>")
btv.keymap.set("n", "@", "<F3>")
```

which works because the recording captures a mapping's *LHS* and replays through
the matcher (see below). `Q` (neovim's replay-last) is not bound at all —
`<F3><F3>` is that command.

Plus the surfaces that make them usable: `recording @a` on the message line, a
`btv.macro.*` Lua surface, a statusline segment, shada persistence (free — a
macro is just a register), and abort-on-failure so `100<F3>a` stops at the end of
the buffer instead of grinding on the last line.

## The two design decisions

### 1. A macro register holds bemtvi **key notation**

Vim stores raw bytes (a literal `0x1b` for `<Esc>`, its `K_SPECIAL` escape for
`<F5>`). bemtvi already speaks one lossless, human-readable key encoding
everywhere — `parse_keys` / `key_to_notation` — and `key_to_notation` is a true
round trip (a typed `<` is written `<lt>`, a modified `>` as `<C-gt>`), so a
recorded macro is stored as `ciwfoo<Esc>` and re-parsed with `parse_keys`.

Consequences, all wanted: `"ap` pastes something readable and editable, a macro
can be *authored* by hand (`btv.reg.set("a", "ciwfoo<Esc>")`), and shada
persistence, `:registers`, and the register mirror need no macro-specific code.
The one departure from vim: `<F3>a` on a register holding ordinary *yanked text*
parses `<...>` forms as keys rather than as literal characters. Documented in
`known-approximations.md`.

### 2. Recording captures **typed** keys, at the point they execute

Vim records the keys the user typed and re-applies mappings on replay. bemtvi
must do the same, because so much of the editor is Lua keymaps (LSP `gd`,
completion triggers, every plugin): recording post-mapping would capture
*nothing* for a Lua-handler map and the replay would silently skip it.

So the recording hook is in the **server** (`EditHost`), where typed keys meet
the keymap matcher — not in `Editor::input`, which only ever sees what the
matcher released. Three sites feed it, and they are exactly the places a typed
key reaches the editor:

| site | what is recorded |
| --- | --- |
| `apply_step(Step::Editor(key))` | the released raw key |
| `apply_step(Step::Fire { lhs, .. })` | the mapping's **LHS** keys (so replay re-fires the mapping) |
| `feed_matcher`'s raw-read bypass | a literal argument (`f{char}`, `r{char}`, `"{reg}`, an operator's motion) |

Crucially the hook fires at **execution** time, not at typed time. That is what
makes the terminating `q` exactly the last key recorded even when the matcher
withheld it behind a live mapped prefix — core just pops it. Recording at
typed time would need to guess how far back to truncate.

A mapping's RHS, `nvim_feedkeys` typeahead, `:normal`, and macro playback
itself are **suppressed** (a depth counter around `fire_mapping` /
`drain_feedkeys` / the playback drain), so a macro records what the user typed,
once.

The key *buffer* nevertheless lives in **core**, next to the register file: the
server's hook is a one-line `editor.note_macro_key(key)`. Core owns start,
stop, truncation, the register write, and `recording_register()`; the server
owns only "here is a typed key" and the replay drive. This keeps the whole
feature inside the core/edit-host pair that native, daemon, and wasm all share
— tier-1 remote support falls out for free.

### Replay must go back through the matcher

Because the recording holds mapping LHS keys, playback cannot recurse through
`Editor::input` (the `:normal!` path) — it has to re-enter the server's matcher.
Core therefore *requests* playback (`take_macro_play()`) and the server drives a
playback **stack** (nesting `<F3>b` inside `<F3>a`, `{count}<F3>a` as a repeat counter on
the frame rather than an expanded key list, depth- and budget-capped like
`drain_feedkeys`).

## Phases

### Phase 1 — recording  *(landed)*

* core `command.rs`: `Stage::RecordPending`, `ResolvedCommand::MacroRecord`,
  which-key continuations for the `<F2>` prefix (reuse `register_continuations`).
* core new `macros.rs`: `macro_record: Option<(char, Vec<Key>)>`,
  `note_macro_key`, stop → `key_to_notation` join → `set_register_api(charwise,
  append = uppercase name)`, `recording_register()`.
* core `view.rs`: project `recording @a` onto the message line when idle
  (the `-- TERMINAL --` precedent — no client change).
* server `input.rs` / `keymap.rs`: the three record sites, `Step::Fire { lhs }`,
  the suppression counter.
* tests `crates/bemtvi-server/tests/editing/macros.rs`: contents of the register
  after a record; `<F2>A` appends; the trailing `<F2>` is not recorded; insert-mode
  keys are recorded; a Lua-map LHS is recorded (and its RHS is not recorded
  twice); recording survives a withheld mapped prefix.

### Phase 2 — playback

* core: `<F3>{reg}` (`Stage::PlayPending`), `<F3><F3>`, `<F3>:`, `{count}<F3>`,
  `E354` for a bad register name, playback request queue.
* server: the playback stack + drain, ahead of the feedkeys typeahead, nesting
  cap, suppression while playing.
* tests: replay of an edit macro; `3<F3>a`; `<F3><F3>`; a macro that fires a Lua
  keymap; a macro recorded in insert mode; a nested `<F3>b`; a self-recursive
  macro terminates.

### Phase 3 — abort on failure

`100<F3>a` must stop when the macro's motion runs out of buffer. bemtvi has no
bell today (`jumps.rs`: "vim beeps; bemtvi has no bell"), so this phase adds
the missing signal at the canonical layer: `Editor::beep()` + a
`command_failed` flag cleared per input, set by the loud `E###` echo path *and*
by the silent-failure sites vim beeps at (a vertical motion already at the
buffer edge, `f`/`t` miss, an unset mark, an exhausted undo). Playback checks
it after every key and drops the remaining frames.

### Phase 4 — surfaces, docs, remote

* `btv.macro.recording()` / `btv.macro.executing()` / `btv.macro.play(reg, n)`,
  the `vim.fn.reg_recording()` / `reg_executing()` aliases, a built-in
  `macro` statusline segment.
* `known-approximations.md` (drop "as are macros", add the notation departure),
  the book, `examples/macros/`.
* Verify in **both** builds: `--no-default-features` (wasm edit-host) and a
  daemon test, per the tier-1 rule.
