# Marks — `m{x}` set, `` `{x} `` / `'{x}` jump, special marks & `:marks`

Today nxvim has no marks. This plan adds vim's mark system: setting a mark with
`m{a-zA-Z}`, jumping to a mark's exact byte position with `` `{x} `` (charwise
exclusive) or to the first non-blank of its line with `'{x}` (linewise) — both
usable as **operator targets** (`` d`a ``, `y'a`) since they are ordinary
motions. It covers the buffer-local lowercase marks `'a`–`'z`, the global
cross-buffer file marks `'A`–`'Z`, the automatic special marks (`` `` `` / `''`
last jump, `` `. `` last change, `` `^ `` last insert, `` `[ `` / `` `] `` last
yank-or-change bounds, `` `< `` / `` `> `` visual bounds), the `:marks` display,
and the `setpos`/`getpos`/`nvim_buf_{set,get}_mark` Lua surface.

The unifying syntax is the `m` set-prefix and the `` ` `` / `'` jump-prefixes,
each consuming the **next key as a mark name** — exactly the "next key is data"
grammar stage that `"x` registers, `f{char}`, and `r{char}` already use.

## Why this is feasible now (de-risking facts)

Verified in the current tree before planning:

- **Marks are motions, and the operator path already takes any motion as a
  range.** `resolve_motion` (`motions.rs:125`) returns a `MotionResult { target:
  usize, kind, axis }`; `apply_resolved_motion` (`command.rs:928`) feeds that
  result to `apply_operator` when an operator is pending. So adding
  `Motion::MarkJumpExact(char)` / `Motion::MarkJumpLine(char)` makes `` d`a `` /
  `d'a` / `y'a` work for free — no operator-side change. `'` reuses the existing
  first-non-blank landing: `MoveAxis::LineAnchor` already sets `col =
  first_non_blank(line)` (`motions.rs:248`), the same axis `gg`/`G` use
  (`motions.rs:189`).
- **The cursor is a plain `(line, col)` pair and there is one canonical setter.**
  `Cursor { line, col }` (`mod.rs:86`); jumps land via `set_cursor_char(idx)`
  (`cursor.rs:160`), which derives line/col from a byte offset and snaps to a
  grapheme boundary. A mark is therefore just a stored `Cursor`, and jumping is
  `set_cursor_char(line_start(mark.line) + mark.col)`.
- **The command grammar already has clean "next key is data" stages.** The
  `Stage` enum (`command.rs:277`) has `FindPending`, `ReplacePending`,
  `TextObjectPending`, `RegisterPending`, … and `parse_step` (`command.rs:406`)
  consumes the next key as raw data for each. `Stage::MarkSetPending` (after `m`)
  and `Stage::MarkJumpPending(kind)` (after `` ` `` / `'`) are exactly this
  shape. Because the keymap oracle `command_status` folds the *same* `parse_step`,
  `m`, `` ` ``, `'` get correct prefix/complete disambiguation for free (the
  take-latest harness note in CLAUDE.md is unaffected — this is pure grammar).
- **Buffer-local state already has a home, and buffer-switch already
  saves/restores per-buffer cursor.** Each `OpenBuffer` (`mod.rs:155`) carries
  `saved_cursor: Cursor` (`mod.rs:174`) restored on switch; buffer-local marks
  (`a`–`z`) live right beside it. Buffers carry a stable `BufferId(u64)`
  (`mod.rs:95`) — the key for global file marks.
- **There is a precedent for editor-state "specials" projected on read.** The
  registers feature computes `"%` / `"/` / `":` / `".` from existing editor
  state rather than storing them (see `2026-06-07-registers.md` → *Read-only
  specials*). The automatic marks (`` `` ``, `` `. ``, `` `< `` …) follow that
  pattern: derived from search/insert/visual/change state, not a separate store.
- **No Lua mark surface exists yet** — `grep` finds no
  `nvim_buf_set_mark` / `setpos` / `getpos` / `getmarklist` (not even a
  `vim._notimpl` stub). Phase 5 invents the seam; nothing to conflict with.

## Architecture

### The mark store: buffer-local `a`–`z`, global `A`–`Z`

```rust
// On Buffer (buffer.rs) — buffer-local marks, follow the buffer AND ride the
// single edit choke point `Buffer::record` so they track edits (see Phase 2):
marks: HashMap<char, (usize, usize)>,    // 'a'..='z' as (line, col)

// On Editor (mod.rs) — global file marks, point at a (buffer, position):
global_marks: HashMap<char, (BufferId, Cursor)>,   // 'A'..='Z'  (and '0'..='9' later)
```

> Phase 1 first put the buffer-local marks on `OpenBuffer` as a `Cursor`; Phase 2
> moved them onto `Buffer` (as `(line, col)`) so they ride the `record` edit choke
> point the way `extmarks` do — the only way to track edits without an
> easy-to-miss editor-side hook. They still follow the buffer across switches,
> since `Buffer` *is* the per-buffer state.

A `Position { buf: Option<BufferId>, cursor: Cursor }` newtype unifies the two
on lookup. Setting `m{a-z}` writes the *current buffer's* `marks`; `m{A-Z}`
writes `global_marks` keyed by `(current BufferId, cursor)`. Jumping to a
lowercase mark reads the current buffer's map; jumping to an uppercase mark
**switches to its buffer first** (reusing the existing buffer-switch path that
saves/restores `saved_cursor`), then lands the cursor.

A small pure module `crates/nxvim-core/src/editor/marks.rs` owns the *routing
and validation* (which names are buffer-local vs global, which are read-only
automatics, name validity → loud `E20: Mark not set` / `E21`-style errors),
mirroring how `registers.rs` concentrates the vim routing rules in one tested
place. The `Editor` methods stay thin: `set_mark(name)`, `mark_position(name) ->
Option<Position>`.

### The `m` / `` ` `` / `'` prefixes in the grammar

`parse_step` (`command.rs:406`) gains three keys and two stages:

1. `m` (in `Stage::Start`, normal mode) → `Prefix`, `stage = MarkSetPending`.
   The next key is the mark name → emit a `ResolvedCommand::SetMark(char)`;
   an invalid name is a dead-end `Reset` (loud-by-construction, like find).
2. `` ` `` → `Prefix`, `stage = MarkJumpPending(Exact)`; `'` → `stage =
   MarkJumpPending(Line)`. The next key is the mark name → emit
   `Motion::MarkJumpExact(name)` / `Motion::MarkJumpLine(name)`.

Because these are motions, the operator-pending path (`` d`a ``) is automatic.
`SetMark` is a non-motion command handled in `execute_normal`.

### Jump semantics & the `` `` `` / `''` previous-context mark

- `` `{x} `` — **charwise exclusive** motion to the mark's exact `(line, col)`.
- `'{x}` — **linewise** motion landing on first-non-blank
  (`MotionResult::linewise(line_start, MoveAxis::LineAnchor)`).
- A mark that is not set resolves to `None` → the motion fails *loudly* (vim:
  *E20: Mark not set*), never a silent no-op that leaves the cursor put.
- Any **jump** records the pre-jump cursor into the previous-context mark
  (`` ` `` / `'`, i.e. `` `` `` / `''`). A single stored slot
  (`prev_context: Option<Position>` on the buffer) suffices — the full
  `<C-o>`/`<C-i>` jumplist *stack* is deferred (Phase 6). "Jump" = the jump-class
  motions only (`G`, `gg`, `/`?`/`n`/`N`, `` ` ``/`'` themselves, `:line`), not
  ordinary `h`/`j`/`k`/`l`/word motions — matching vim's jump definition.

### Marks track edits (the faithfulness requirement)

Marks are positions in *text*, so inserting or deleting lines above a mark must
shift it, and deleting the marked line drops the mark. Storing a bare `Cursor`
that never moves is a **silent approximation** — the mark would drift and point
at the wrong line after any edit, looking like it works while being wrong (the
exact failure mode CLAUDE.md's no-silent-stubs rule targets). So mark adjustment
is a first-class phase (Phase 2), not an afterthought, and until it lands the
store carries an `INCOMPLETE:` tag stating "marks do not yet track edits."

## Phases

### Phase 1 — Mark store + `m{x}` set + `` `{x} `` / `'{x}` jump (buffer-local `a`–`z`) — DONE

The end-to-end core: set a lowercase mark, jump to it exactly and linewise, use
it as an operator target.

- New `crates/nxvim-core/src/editor/marks.rs`: name classification (Phase 1
  accepts only the buffer-local lowercase `a`–`z`; every other name is a loud
  grammar dead-end until its phase lands), plus `Editor::set_mark` /
  `mark_position`. `marks: HashMap<char, Cursor>` added to `OpenBuffer`.
- Grammar: `Stage::MarkSetPending`, `Stage::MarkJumpPending(MarkJumpKind)` in the
  `Stage` enum; the `m` / `` ` `` / `'` arms in `parse_step`;
  `Motion::MarkJumpExact(char)` / `MarkJumpLine(char)` resolved in
  `resolve_motion` — exact = charwise-exclusive to `byte_at(mark.line, mark.col)`,
  line = `MotionResult::linewise(line_start(mark.line), MoveAxis::LineAnchor)`.
  Because they are motions, `` d`a `` / `d'a` / `y'a` work through the existing
  operator path with no operator-side change.
- `execute`: `ResolvedCommand::SetMark(name)` → `self.set_mark`. A jump to an
  unset mark resolves to `None` and is reported loudly (*E20: Mark not set*) in
  the motion-miss arm, aborting any pending operator — never a silent no-op.
- **Tests** (`editing.rs`, all passing): `ma` then `` `a `` round-trips to the
  exact (line, col); `'a` lands first-non-blank; `` d`a `` deletes the exclusive
  range ("hello " → "world"); `d'a` deletes the linewise range; a jump to an
  unset mark echoes E20 and leaves the cursor put.
- **Deferred to a later phase, noted to stay honest:** the ex-range mark address
  `:'a,'bd` still fails loud (`ex.rs` `parse_ex_range`) — buffer-local marks now
  exist, but wiring them into the ex-range parser rides with Phase 4. Until
  Phase 2 lands, stored marks do **not** track edits (the `INCOMPLETE:`-class
  caveat from *Architecture*); the Phase-1 tests avoid editing above a live mark.

### Phase 2 — Marks track edits (faithfulness) — DONE

Make stored marks shift with text changes so they stay correct.

- **Implemented by riding the real edit choke point, not a `normalize` hook.**
  `Buffer::normalize` is *not* a chokepoint (~12 call sites); the single edit
  funnel every path goes through is `Buffer::record` (the tail of `insert` /
  `remove`), which already shifts `extmarks`. So the buffer-local marks moved
  *onto* the `Buffer` (a `marks: HashMap<char, (line, col)>`, mirroring how
  `extmarks` live on the buffer for exactly this reason) and a sibling
  `shift_marks(start_point, old_end_point, new_end_point)` runs from `record`.
  This is strictly better than the originally-sketched
  `adjust_marks(start_line, delta_lines)` editor-side hook: it cannot miss an edit
  path, and it gets within-line column shifts and the line-drop for free from the
  `BufferEdit` points already computed for tree-sitter.
- **Shift rule (on `(row, col)` points, since marks are line-oriented):** a mark
  before the edit is untouched; a mark at/after the edit's old end slides by the
  row delta (and the column delta too if it sat on the old-end row), giving a line
  inserted/deleted above a row-shift, text inserted/deleted earlier in the line a
  column-shift, and a pure insert *at* the mark right-gravity; a mark inside the
  replaced region is **dropped** when its line is swallowed (`old_end.row >
  mark.row`, e.g. `dd` on the marked line) and otherwise collapses to the edit
  start (a within-line `cc`/delete). See `crate::buffer::shift_marks`.
- **Undo/redo:** `Snapshot` now carries `marks` alongside `extmarks`; `restore`
  re-installs them after `mark_resync` (which clears both — correct for a genuine
  reload, where there's nothing to restore from). So marks ride back to their
  positions on undo, matching vim.
- Phase-1 `INCOMPLETE:` tag removed.
- **Tests** (`editing.rs`, all passing): `O` a line at the top shifts a mark down;
  `dd` on a line above shifts it up; `dd` *on* the marked line drops it (`` `a ``
  then errors *E20* and the cursor stays put); an insert earlier in the marked
  line shifts the column; and a mark rides back to its position on `u`.

### Phase 3 — Global file marks `A`–`Z` (cross-buffer)

- `global_marks: HashMap<char, (BufferId, Cursor)>` on `Editor` (`mod.rs`).
  `m{A-Z}` records `(current buf, cursor)`; jumping to it switches to that buffer
  via the existing buffer-switch (which already saves/restores `saved_cursor`,
  `mod.rs:174`) before landing. If the buffer was closed, the mark errors loudly.
- **Tests** (`editing.rs`): open file A, `mA`; `:e` file B; `` `A `` switches back
  to A at the marked spot; `'A` from B lands first-non-blank; uppercase mark
  survives a buffer switch where a lowercase one would not (lowercase is
  per-buffer).

### Phase 4 — `:marks` display + automatic / special marks

- `:marks [names]` ex command (dispatch in `ex.rs:194`, impl beside the
  `:registers` panel builder): a table `mark / line / col / file-or-text`,
  optional name filter, rendered via the existing message/panel surface.
- Automatic marks, **projected from existing state** (no new store) like the
  register specials: `` `` `` / `''` (previous-context slot from Phase 1's jump
  recording), `` `. `` (last change — capture on edit), `` `^ `` (last insert
  position — capture on `<Esc>` from insert, reusing the same hook the `".`
  register uses), `` `[ `` / `` `] `` (bounds of last yank/change), `` `< `` /
  `` `> `` (last visual selection — read the visual-mode anchor/cursor already
  tracked). Writing these via `m` errors loudly (read-only, E-style).
- **Tests** (`editing.rs`): `:marks` lists set marks; after a jump `` `` `` /
  `''` return to the prior spot; `` `. `` after an edit; `` `^ `` after insert;
  `gv`-relevant `` `< `` / `` `> `` after a visual selection; `` `[ `` / `` `] ``
  around a just-yanked region.

### Phase 5 — Lua / RPC surface

- `nvim_buf_set_mark(buf, name, line, col, opts)` /
  `nvim_buf_get_mark(buf, name)` (`(row, col)`), bridged to core like the other
  `nvim_buf_*` calls; `vim.fn.setpos` / `getpos` (`'.'`, `"'a"`, `"'A"`),
  `vim.fn.getmarklist(buf?)`. Fill them as real implementations, not
  `vim._notimpl` stubs.
- **Tests** (`editing.rs`): `nvim_buf_set_mark` then `` `a `` jumps there;
  `nvim_buf_get_mark` round-trips a `ma`; `getpos("'a")` / `setpos`; `getmarklist`
  enumerates set marks.

## Phase 6 (later) — jumplist, changelist, numbered marks

- **Jumplist `<C-o>` / `<C-i>`** — the full stack behind `` `` ``: each jump
  pushes the prior position; `<C-o>` walks back, `<C-i>` forward. Phase 1 stores
  only the single previous-context slot; this generalizes it to a bounded ring.
  Its own feature (motion-recording engine), tracked separately.
- **Changelist `g;` / `g,`** — sibling of the jumplist over edit positions
  (`` `. `` is its head).
- **Numbered marks `'0`–`'9`** — set on exit, restored from a shada/viminfo file
  across sessions; needs a persistence layer nxvim does not have yet.

## Out of scope (for now)

- shada/viminfo persistence of global and numbered marks across runs.
- `:delmarks` / `:delmarks!` (mark deletion) — a small follow-up once the store
  exists; not needed to exercise the feature.
- `g'` / `g`` (jump without changing the jumplist) — trivial once the jumplist
  lands in Phase 6.
- Sign-column / `gutter` mark indicators — a UI concern, unrelated to motions.
