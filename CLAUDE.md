# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

nxvim is a modal, vim-style editor in Rust — its own editor, not a neovim build: a headless, async editor **server** with thin UI **clients**, talking over nxvim's own msgpack-RPC. Editing behavior tracks vim/neovim, but every API is nxvim's own: config and plugins target the `nx.*` Lua namespace ([the `nx` API](docs/specs/2026-06-11-native-plugin-api.md); [ADR 0002](docs/decisions/0002-native-plugin-system.md)), and the only `vim.*` Lua is the bounded glue that runs **neovim colorschemes** unmodified (the sole neovim plugin surface) plus a closed whitelist of muscle-memory aliases (`vim.g`/`vim.o`/`vim.opt`, `vim.cmd`, `vim.keymap.set`, autocmd/user-command/hl registration, `vim.notify`, pure `vim.tbl_*`-style helpers, … → their `nx` equivalents; the canonical list is ADR 0002). The authoritative design doc is **[docs/architecture.md](docs/architecture.md)** — read it first for the crate layout, client-server model, the RPC + `View` protocols, the rope text model, the Lua bridge, and the roadmap. This file only adds the commands and the conventions that aren't obvious from the code itself.

## Commands

```sh
# Build / run
cargo build                         # debug build of the whole workspace
cargo build --release               # release profile uses thin LTO (slower to build)
cargo run -p nxvim -- file.txt      # run the editor; the file argument is optional

# Test — everything is a black-box integration test (see "Conventions" below)
cargo test --workspace
cargo test -p nxvim-server --test editing <name>   # run a single test by name / substring

# Lint & format — both are enforced by the pre-commit hook
cargo fmt --all                     # format in place ( add `-- --check` to verify only )
cargo clippy --all-targets -- -D warnings
```

**The Lua backend is vendored PUC Lua 5.4 — the only backend.** LuaJIT was dropped; nxvim is PUC-Lua-only, matching the wasm build (which never supported LuaJIT). There is no backend Cargo feature to select — `lua54` is baked into the shared `mlua` dependency in the root `Cargo.toml`. (5.4 brings real 64-bit integers, native bitwise ops, the `utf8` library, **yieldable `pcall`**, and a generational GC over the prior 5.1 baseline; a one-line `loadstring = loadstring or load` compat shim in `runtime.rs` covers the only stdlib removal that touched the prelude.) Lint and test on the **default features** as shown above. (`nxvim-server`'s `native` feature is default-on and only turned *off* for the wasm edit-host via `--no-default-features`; it gates the async/transport tree, not the Lua VM.)

A pre-commit hook (`.pre-commit-config.yaml`) runs `cargo fmt --check` + `cargo clippy -D warnings` on every commit. After a fresh clone, run `pre-commit install` once to enable it; bypass in an emergency with `git commit --no-verify`.

`vendor/neovim` is a git submodule kept purely as a behavioral/source-layout reference — it is never built or linked. It is not needed to build nxvim; populate it only if you want the reference: `git submodule update --init vendor/neovim`.

## Workflow

- **Bug fixes are test-driven.** For every bug-fix request, first write a test that *fails* while the bug exists and *passes* once the fix is in place. Confirm it fails, implement the fix, confirm it passes, then coordinate with the requester to validate the behavior. A test written before the fix proves the bug is real and that the fix isn't a no-op, and it guards against regression. (See the testing conventions below for where tests live.)
- **Big features go one phase at a time.** For a major feature, first persist a plan under `docs/plans/<date>-<feature>.md`, then implement one phase at a time — commit and pause for review between phases rather than landing the whole thing at once.
- **Ship a runnable example when finishing a config/keymap-facing feature.** On top of the automated tests, add `examples/<feature>/` — an `init.lua` (numbered sections, each with a *type-this / see-that* note) plus a `sample.txt`. Run it with the config isolated from the real one: `NXVIM_CONFIG=examples/<feature> cargo run -p nxvim -- examples/<feature>/sample.txt` (discovery order is `$NXVIM_CONFIG` → `$XDG_CONFIG_HOME/nxvim` → `~/.config/nxvim`). Verify every example fires end-to-end before handing it over — but the end-to-end check is a **throwaway**: do **not** commit Rust tests that load an `examples/` config (no `include_str!` / `config_dir` pointed at `examples/`). The `examples/` dirs stay; feature behavior is covered by the normal (non-example) suites.

## Design principles (how to decide what to build)

- **Dogfood the `nx.*` plugin API — prime directive.** Everything that can reasonably be an `nx.*` Lua plugin *is* one; the editor's own first-party features (fuzzy picker, completion, statusline, snippets, tree docks, and behavior layered on them) ship as bundled `nx` plugins, not bespoke Rust. Rust keeps only what a plugin *cannot* be: the pure synchronous core, the frame/renderer, and the native engines (treesitter, LSP, regex). The server exposes a native *provider registry* (the seam); the feature driving it is a plugin. If a feature can't be expressed against `nx.*`, that's a gap to close in the API, not a reason to reach behind it — only drop to Rust for a genuine engine/frame/core constraint, and say which. (architecture.md guiding principle #3; ADR 0002 decision #5.)
- **There is no neovim compatibility — port behavior natively.** When a request cites a neovim plugin (telescope, which-key, cmp, lazy, …), treat the plugin as a *behavioral spec to reimplement* on nxvim's native surfaces (core editor + `nx.*`), never as something to install or run under a compat layer. The `vim.*` surface is only colorscheme glue plus muscle-memory aliases; any "telescope/cmp/lazy works" notes are overstated compat-history, not real tools.
- **Reuse existing machinery before adding new APIs.** nxvim already has rich native surfaces (quickfix/loclist stack, docks + TabStack, picker sources, the `nx.*` Lua API). Map a new feature onto existing structs, ex-commands, and Lua APIs first; justify every genuinely-new API by showing no existing surface covers it. Don't build a parallel mechanism (e.g. a new named-list registry) when per-window location lists + dock tabs already give it.
- **Fix at the canonical layer, never route around a gap with a heuristic.** When a plugin (or any higher layer) needs a fact the core *should* expose but doesn't yet, close the gap in the core — don't sniff a proxy for it. The tell is a heuristic that re-derives something the engine already knows structurally: pattern-matching a buffer's *name* to guess it's a scratch panel, parsing a rendered string to recover state, keying off a filetype to infer a buffer kind. If a real, canonical signal exists (or can be modelled cleanly), thread *that* through — even when it costs a cross-crate change — because the heuristic silently rots (a real file literally named `[foo]`, a renamed filetype) and every future caller re-invents the same guess. Worked example: nxvim-line skipped git on scratch panels by testing `name:match("^%[.*%]$")`. The canonical signal is `'buftype'`, which the core already had but returned `""` for `nofile` surfaces (an admitted gap in `quickfix.rs::buffer_buftype`). The fix modelled `nofile` in the core (structurally, via `is_listed_buffer`), mirrored `'buftype'` through `BoMirror` → `nx.bo[buf].buftype`, and let the plugin gate on `buftype == ""` the neovim way — four layers touched, one heuristic deleted, and `nx.decor` + every future plugin got the real signal for free. Before committing to a heuristic, ask whether a canonical fix exists and is reachable; if it is, take it (and if the scope is large, surface the trade-off rather than defaulting to the hack).
- **Generally-useful helpers go in public `nx.utils.*`.** A broadly-useful utility (debounce/throttle, pack/partition, path munging) that isn't a data helper (`nx.tbl`/`nx.list`/`nx.str`/`nx.iter` in `prelude/stdlib.lua`) or a feature API belongs under `nx.utils.*` in `prelude/utils.lua` — documented and tested standalone, then consumed by the feature — not inlined as one plugin's private. Match the prelude's vararg idiom (`{ ... }` + `select("#", ...)`, not `table.pack`).
- **The editor must never freeze.** Any per-event handler (PTY burst, file load, paste, redraw) whose cost scales with the *total* buffer/output size is a bug — a flood turns O(N)-per-event into O(N²) and hangs the UI. Keep per-event work incremental/bounded (project once per repaint, not per input chunk; re-read only what changed; materialize expensive derived state lazily). Regression-guard heavy paths with a large-flood test that must complete fast. (See `crates/nxvim-server/src/terminal.rs` for the worked example.)
- **The remote session is a tier-1 target — everything must work over it.** A daemon (`--connect-daemon`) or web/wasm session is not a degraded mode: any feature that works locally must work identically over the wire, and "it's only remote" is never a reason to punt (or to fail loud with a "not supported remotely" stub — that's a bug, not an acceptable limitation). The reason it's (almost) always achievable: the whole editing core — including the encoding seam, the rope, options, and most derived state — runs *core-side* regardless of where the bytes come from; the daemon only ships raw bytes / fs results off-tick. So a feature that looks "local-only" usually just needs its parameter carried from the point a request is deferred (`PendingOpen`, `PendingSave`, a `Loop`/`Control` op) to the point the async result lands (`apply_open` / `load_replica_bytes` / `load_replica_wasm`), bridged by a per-buffer/per-token map on `EditHost` when the landing is keyed by id alone (see `forced_fetch_enc` for `:e ++enc=`, `reload_posts`, `pending_replica_edits`, `pending_chdirs`). Verify a new feature in **both** builds — native (`--test daemon_edit`/`daemon_fs`/`daemon_save`) and wasm-eligible (`--no-default-features`, plus the `verify-*.mjs` browser checks) — not just the synchronous local path. This is the *why* behind the shada cfg-split convention below; the tier-1 rule is the general form.

## Conventions that will bite you if missed

- **No silent stubs or skips.** Every unimplemented function, missing piece, or unsupported path must fail *loud* — raise/error with the name of what's missing — never return a fake/empty value or silently no-op. A stub that quietly succeeds makes broken behavior look like working behavior (e.g. an LSP server that "starts" but ignores its config). If something can't be done yet, say so at runtime. (See `docs/plans/2026-06-05-lsp-completion.md` for the LSP application of this.)
- **No unit tests.** Behavior is verified end-to-end through the running server: a test starts a real server over an in-process RPC pipe, feeds vim key-notation via `nx_input`, and asserts on `nvim_buf_get_lines` / cursor / the `redraw` view. The shared harness — `crates/nxvim-test-harness` (a dev-dependency of both `nxvim` and `nxvim-server`) — provides the common primitives: `spawn`/`attach`/`start_attached`, `feed`/`lines`/`cursor`/`exec_lua`, the redraw accessors in both conventions (raw `params: &[Value]` and extracted `map: &[(Value, Value)]`), and the temp-file / `serial_lock` / `FakeClipboard` helpers. Import what you need from `nxvim_test_harness` rather than re-defining it. Put new coverage in the relevant `tests/*.rs` file (the big suites are split into submodules, e.g. `tests/editing/<concern>.rs` behind a thin `tests/editing.rs` entrypoint, with cross-section helpers in that suite's `support.rs`) — do **not** add `#[test]` unit tests inside the crates. (Rationale: architecture.md → *Testing philosophy*.)
- **Redraw test helpers must take the *latest* queued `redraw`, never the first.** A `redraw_after(keys)`-style helper feeds input, sends an `nvim_get_mode` barrier, then reads a `redraw` off the `incoming` notification channel. The client's reader task ferries the wire into `incoming` asynchronously, so under load (`cargo test --workspace` runs many binaries while compiling) it lags and a stale frame — the startup repaint, or a previous call's trailing barrier repaint — can sit *ahead of* this input's frame. Taking the first returns the stale one → flaky, test-shuffling failures (a different test fails each run; passes serially / with `--test-threads=4`). Drain to the most recent redraw (`drain_to_latest_redraw`) with a bounded poll-retry instead of panicking on the first empty channel. The barrier's trailing repaint is state-identical for *persistent* state (message / lines / flags), so "latest" is correct — **except** one-shot transient fields (the `scroll` gesture) live only in the input's frame; for those keep the latest redraw matching a predicate (e.g. `scroll_after` → `scroll(map).is_some()`). This is a client-side harness race, **not** a server `tokio::select!` ordering issue, so `biased;` does not fix it. (The take-latest pattern lives in `nxvim-test-harness` — `drain_to_latest_redraw` / `drain_latest_redraw` / `redraw_after`; use those rather than re-implementing a take-first variant.)
- **Keep the harness `incoming` receiver alive for the test's lifetime.** `spawn`/`attach`/`start_attached` return `(Rpc, UnboundedReceiver<Incoming>)`. Dropping the receiver closes the client's read side — the reader task's `in_tx.send` fails on the next server notification, tearing down the connection, so the *next* RPC request fails `"rpc connection closed"` (surfaces as a client-side panic in `exec_lua`, with no server panic — looks like a server crash but isn't). A helper written `let (rpc, _incoming) = ...; rpc` drops it at scope end. Bind and hold it even when a test asserts only via `exec_lua` and never reads `redraw`: `let (rpc, _incoming) = start().await;`. Symptom: *every* test fails `"connection closed"` on its **first** request.
- **Tests must be hermetic** — no dependence on the developer's local environment. Never resolve `~/.config/nxvim` or `~/.local/share/nvim` in a test. nxvim hosts no neovim plugins (the compat runtime and its `clone_plugin`/`PLUGIN_PINS` harness helpers were ripped out), so tests never clone upstream plugins — cover pure-`nx.*` behavior end-to-end through the harness instead. Spawning the real `nxvim` binary (PTY e2e)? Point `NXVIM_CONFIG` at a throwaway empty dir (`empty_config_dir` in `crates/nxvim/tests/e2e.rs`) so it never reads the real config; those PTY tests need a real TTY and are `#[ignore]`d (`cargo test -p nxvim --test e2e -- --ignored`). Skip-if-missing (`eprintln!("skip: ...") + return`) is the convention for an unavailable external dependency (e.g. the `lua-language-server` binary).
- **Mocks must react to inputs.** A test that passes regardless of whether the feature works is worthless. A mock that returns a fixed reply *ignoring the request's inputs* (cursor position, document text, typed prefix) proves nothing — e.g. the LSP mock (`crates/nxvim-lsp/src/mock.rs`) tracks the document via `didOpen`/`didChange` and answers completion from the actual prefix at the cursor. Assert on the inputs the editor actually sent, and confirm a regression genuinely fails by mutation-testing (break the code, watch the test fail). Static/scripted replies are acceptable only for narrow client-side mechanics needing precisely-controlled items (sort order, an explicit `textEdit`, a paint).
- **"Loads / doesn't crash / resolves / compiles" is not "works."** Before reporting a feature done, verify the actual behavior end-to-end (the server honors its settings, the feature produces the right result), not just the absence of errors. State the weaker claim precisely when that's all you've shown, and distinguish real implementations from stubs/approximations explicitly. (Pairs with the "no silent stubs" rule above.)
- **Disk-change tests must round-trip the precondition before the external write.** nxvim arms a native file watch on every file-backed buffer that auto-runs `:checktime` when the file changes on disk (autoreload / W11/W12/E211). It fires *asynchronously* relative to the test's own actions, so a test that does fire-and-forget `feed(&rpc, ...)` to set up a precondition (modify the buffer, `:set noautoread`) and then `std::fs::write`s the file races the watch. Force the precondition to land server-side first with a synchronizing round-trip (`lines(&rpc).await` after a modify; `exec_lua(.., "return vim.o.autoread")` after `:set noautoread`). When asserting a message the watch's W12 might overwrite, target it with `redraw_after_matching` rather than drain-to-latest. The product behavior is correct; these are test-ordering fixes.
- **`nxvim-core` stays pure and synchronous** — no async, no I/O beyond `Buffer` file read/write, no transport types. All async / RPC / Lua lives in `nxvim-server` and above, so every front end shares identical editing behavior.
- **Dependencies are pinned exactly** (`=x.y.z`) in the root `Cargo.toml` under `[workspace.dependencies]`. Add a new dependency there with an exact version, then pull it into a crate with `<dep>.workspace = true`.
- **Indexing is byte-offset based and the rope always keeps a trailing `\n`** (so `line_count == rope.len_lines() - 1`; the final phantom line is never edited or shown). Call `Buffer::normalize()` after mutations to preserve the invariant. (Details: architecture.md → *Text model*.)
- **`nx.*` prelude docstrings are extracted into the book as markdown — write them as valid markdown.** The book generator (`book/gen/generate.py` → mdBook) pulls each public function's `--` doc-comment straight onto a rendered API page, so source-only comment formatting renders wrong. Three rules keep them clean: (1) **Backtick every bare code token** — identifiers, call-forms, `nx.*`/`vim.*`/`opts.*` names, Rust paths/types, and string literals the API accepts or returns (`"GET"`, `""`, `"<C-n>"`). Left un-backticked, mdBook smart-punctuation corrupts them (`"sha256"` → curly quotes, `--` → en-dash). Leave genuine English scare-quotes (`"go to file"`, `"pretty"`) as prose. (2) **Fence aligned tables and code/option examples** in ` ``` ` / ` ```lua ` blocks — unfenced, an aligned option list collapses into a run-on paragraph and its `--` inline comments get mangled. (3) **Keep each inline code span on ONE source line** — a single-backtick span that wraps across two `--` lines folds the line break and the bullet-alignment indentation *into* the code token when rendered (e.g. `` `Content-Type: application/json` `` splitting mid-span). Reflow prose so no backtick span straddles a line boundary. Verify with `book/gen/generate.py` + `mdbook build` (zero smart-quote-corrupted spans across the API pages).
- **`nx.schedule` can't poll for cross-tick state — use `nx.on_next_tick` / `nx.wait_for` (Lua).** `nx.schedule(fn)` is a *same-convergence* microtask: it runs at the end of the current input tick, so it cannot observe anything that only refreshes *between* server ticks — a freshly-mounted window's id (`view:winid()` / the `nx._view_win` mirror), or any server-repopulated mirror. Re-arming `nx.schedule(self)` to "wait for" such a value just spins within one convergence and the value stays nil forever. (Polling for a *buffer* number works because the bufnr is known synchronously at view-create; a *winid* is not.) For anything cross-tick, use `nx.on_next_tick(fn)` (run on the next loop turn) or `nx.wait_for(predicate, { tries=, interval=, message= })` — a promise that polls between ticks and fulfils with the predicate's truthy value (rejects when bounded `tries` run out). All three live in `crates/nxvim-lua/src/prelude/{runtime,promise}.lua` alongside `nx.timer`.
- **Regex is PCRE by default, NOT vim syntax — don't write vim-escaped patterns.** The `'regexsyntax'` option defaults to **`pcre`** (the Rust `regex` crate), so `/` search, `:substitute`, `search()`, and any pattern a config/plugin passes speak PCRE: one-or-more is a **bare `+`**, optional a bare `?`, groups `(...)`, alternation `|`, bounds `{n,m}`, word-boundary `\b`. Vim's *escaped* magic (`\+`, `\?`, `\(`, `\|`, `\{`, `\<`/`\>`) is **wrong** here and silently mismatches — `%s/\s\+$//` does NOT trim trailing whitespace (`\+` is a literal `+` in PCRE); the correct pattern is `%s/\s+$//`. The vendored real-vim engine (`nxvim-regex`, `regexp.c`) is **opt-in**: `:set regexsyntax=vim` *and* it's behind the non-default `vim-regex` Cargo feature (it pulls in a C build). `RegexEngine::{Pcre,Vim}` in `search.rs` picks per the effective `'regexsyntax'`; character classes (`\s`, `\d`, `\w`) and `*`/`.`/`^`/`$` happen to spell the same in both, which is what makes a vim-escaped `\+` an easy silent trap. When a substitution "doesn't match", suspect vim-escaping before suspecting an engine bug. (Related memory: [[nxvim-regex-vendored-vim-engine]].)
- **Option-set surfaces have deliberately different unknown-name policy — don't unify them.** `:set <name>` (nxvim's own ex surface) is **strict and fails loud** with `E518`: the registry is `options.rs::canonical()`, and every `apply_set_*` slot has a loud `_ => echo E518` arm (a name in `canonical` but unwired in apply must still fail loud). The guard test `every_known_option_is_wired_not_silent` enumerates the registry — extend its list when you add to `canonical`. But `nx.o`/`vim.o`/`nx.opt`/`nx.go` (the neovim-compat Lua surface) is **lenient: warn-but-store**, NOT a hard error — an unmodeled name lands in the `nx._o_store` catch-all and emits a deduped WARN. This leniency is load-bearing for vim-config/colorscheme compat (`termguicolors`, `background`, `signcolumn`, …); **do not "fix" it into a hard error.**
- **Web/native persist (shada) is a cfg-split — wire new cross-session state in BOTH.** `EditHost` is `#[cfg(feature = "native")]` vs `#[cfg(not(...))]` in `crates/nxvim-server/src/lib.rs`. Native shada flows through the redb flush sites (`shada_checkpoint`/`shada_flush_final`/`shada_write_now`, load `shada_load`), which harvest each field *inline* via the core `Editor::export_persist`. Web/wasm uses a single OPFS JSON blob through the wasm-only `EditHost::export_persist`/`import_persist` (the only callers, via the `eh_export_shada`/`eh_load_shada` FFI in `crates/nxvim-edithost`). State living outside the core `Editor` (e.g. plugin shada in the Lua runtime) must be folded in/out at **both** places, or it persists natively but silently not on web. Verify with `crates/nxvim-edithost/web/verify-shada.mjs`.

## Key files

- `crates/nxvim/src/main.rs` — wires the embedded server (its own OS thread) and the TUI client (main thread) together over a `tokio::io::duplex` pipe, using the same RPC a remote client would.
- `crates/nxvim-server/src/lib.rs` — the `run()` loop; the server is split into focused sibling modules: `dispatch.rs` (the `dispatch()` match defining the `nvim_*` RPC surface), `redraw.rs` (`redraw()` projects the editor `View` into the notification map clients render), plus `evloop.rs` / `excmd.rs` / `input.rs` / `keymap.rs` / `lifecycle.rs` / `effects.rs` / `treesitter.rs` and the `lsp/` subtree.
- `crates/nxvim-core/src/editor/` — the synchronous key / ex-command state machine, where the bulk of the editing logic lives. `mod.rs` holds the `Editor` struct and shared state; the behavior is split into per-concern submodules: `ex.rs` (ex-commands), `command.rs`, `cmdline.rs`, `motions.rs`, `operators.rs`, `insert.rs`, `cursor.rs`, `buffers.rs`, `windows.rs`, `tabs.rs`, `search.rs`, `panel.rs`, `syntax.rs`, `options.rs`, `undo.rs`, plus the newer surfaces: `float.rs` (floating windows), `dock.rs` (permanent docks), `terminal.rs` (in-buffer PTY), `quickfix.rs`, `snippet.rs`, `complete.rs`, `decor.rs` (viewport decorations), `multicursor.rs`, `marks.rs`, `registers.rs`, `jumps.rs`, `persist.rs` (shada), `explorer.rs`, `menu.rs`, `mouse.rs`, `changelist.rs`, `expr.rs`.
- `crates/nxvim-test-harness/src/lib.rs` — the shared black-box test harness (a `publish = false` dev-dependency of `nxvim` and `nxvim-server`): server spawn/attach, the RPC-driving conveniences, the redraw accessors, and temp-fs / lock / clipboard helpers every integration suite shares. It links the same single Lua backend (PUC lua54, via the shared `mlua` dep) as the crate under test, so one backend resolves through the dev-dependency cycle.
